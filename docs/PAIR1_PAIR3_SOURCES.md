# Retrieval and assistance implementation evidence

Official pages were inspected on 29 October 2026. These are implementation sources, not locally reproduced benchmark results. The actual interpreter, package versions, checkpoint revision, configuration, execution device and output hashes belong in each execution record and its environment report.

## Pair 1: image catalogue retrieval

| Model | Primary sources | Licence and implementation |
|---|---|---|
| Marqo-FashionSigLIP | [Official model card](https://huggingface.co/Marqo/marqo-fashionSigLIP), [official OpenCLIP configuration](https://huggingface.co/Marqo/marqo-fashionSigLIP/blob/main/open_clip_config.json), [official wrapper source](https://huggingface.co/Marqo/marqo-fashionSigLIP/blob/main/marqo_fashionSigLIP.py) | Apache 2.0. Fashion-adapted SigLIP encoder; the original selected model is retained. |
| SigLIP 2 Base | [Official model card](https://huggingface.co/google/siglip2-base-patch16-224), [Transformers SigLIP2 documentation](https://huggingface.co/docs/transformers/model_doc/siglip2) | Apache 2.0. Fixed-resolution Base checkpoint at 224 pixels; native processor and encoder are retained. |

The Marqo adapter uses the OpenCLIP implementation suggested by its model card. Its configuration specifies a 224-pixel vision encoder, native image normalization/resizing and a canonicalizing text tokenizer from `timm/ViT-B-16-SigLIP` with context length 64. Acquire and pin that tokenizer repository as well as the Marqo checkpoint. The implementation loads an already acquired local directory through OpenCLIP's `local-dir:` schema, documented in the [official OpenCLIP factory source](https://github.com/mlfoundations/open_clip/blob/main/src/open_clip/factory.py). The selected OpenCLIP version must expose this schema. No repository Python wrapper is executed. `trust_remote_code=True` is unnecessary for this path.

The reviewed Marqo Transformers wrapper imports OpenCLIP and delegates model construction to it. Its published AutoModel route requires executing repository code. This project instead uses the official OpenCLIP route; the wrapper review is contextual and does not grant approval to execute a future changed revision.

SigLIP 2 uses `AutoProcessor` and `AutoModel` with local files and native code. Text is processed with fixed padding/truncation to 64 tokens; image inputs receive the selected checkpoint's native transformation. Embeddings are normalized to unit length and ranked by cosine similarity with product identifiers resolving equal-score ties. Do not interpret these similarities as calibrated relevance probabilities.

Both models index exactly the same image catalogue. Warmups are excluded from per-query timings. The index stores catalogue identifiers and normalized embeddings, with input/configuration fingerprints and an index hash. Saved query predictions include the full ranking and independently supplied qrels. `nDCG@10`, reciprocal rank and `Hit@5` exclude queries without a judged positive item; eligibility counts are reported. Unjudged products receive zero gain, which can bias incomplete judgments. Recall is unavailable unless each query explicitly declares complete qrels and every catalogue product has an explicit judgment. A shortened smoke query set remains labelled `mode: smoke`.

Fashion adaptation creates an important experimental asymmetry. The Marqo card's published Fashion200K results must not be presented as results measured here; Fashion200K overlap also limits claims about unseen-domain generalization.

## Pair 3: grounded shopping assistance

| Model | Primary sources | Licence and implementation |
|---|---|---|
| Phi-4-mini-instruct | [Official model card](https://huggingface.co/microsoft/Phi-4-mini-instruct) | MIT. Native Transformers causal language model; the card identifies Transformers 4.49 as the original integration point. |
| Qwen3.5-4B | [Official model card](https://huggingface.co/Qwen/Qwen3.5-4B), [official configuration](https://huggingface.co/Qwen/Qwen3.5-4B/blob/main/config.json), [Transformers Qwen3.5 documentation](https://huggingface.co/docs/transformers/model_doc/qwen3_5) | Apache 2.0. The selected checkpoint has the `Qwen3_5ForConditionalGeneration` architecture. A sufficiently recent native Transformers implementation is required. |

Use the isolated assistance environment. The checked-in dependency ranges are candidate compatibility constraints; a frozen environment from an actual successful run is stronger evidence than an unexecuted installation specification. The Phi card's historical package example does not establish compatibility with every later combination. Qwen's card asks for current Transformers support; an older version can fail even when another model works. The adapter fails explicitly if the native Qwen3.5 class is missing, and never enables remote code to circumvent that failure.

The primary comparison supplies text tokens only to both models. Qwen is loaded with its published conditional-generation class; its unused vision tower remains loaded, and execution metadata says so. This preserves published checkpoint loading while avoiding unverified remapping of multimodal checkpoint keys into a different class. It does **not** constitute a measurement of the lowest possible memory usage of a language-only runtime.

The final Qwen run completed without a recorded CUDA out-of-memory failure, with native bf16 parameters on `cuda:0`. Its allocator peaks require qualification: peak allocated was **12,179.82861328125 MiB** (`assist-042`), and peak reserved was **13,800 MiB** (`assist-058`), against a diagnostic device capacity of **12,281.5 MiB** (rounded to 12,282 by `nvidia-smi`). These exact counters and their source trace hashes are retained in `environment/assistance-memory-counter-audit.json`; they are not clamped. The development smoke's lower peak cannot represent the full scenario set.

`Measurement` uses synchronized native PyTorch counters, divided by `2**20`; the legacy `_mb` suffix therefore denotes MiB. [PyTorch 2.11's allocated counter](https://docs.pytorch.org/docs/2.11/generated/torch.cuda.memory.max_memory_allocated.html) tracks tensor allocation, while [its reserved counter](https://docs.pytorch.org/docs/2.11/generated/torch.cuda.memory.max_memory_reserved.html) tracks caching-allocator managed memory. Measurements reset peak statistics and include the model/cache baseline already present; trace totals take the maximum across turn inference windows. These counters alone do not establish physical residency. The allocated peak approaches physical capacity and the reserved counter exceeds it, so the completed run cannot establish an all-resident fit with spare physical VRAM. No paging, oversubscription or shared-memory residency measurements were collected, and no cause for the difference is asserted. See the [official memory-management discussion](https://docs.pytorch.org/docs/2.11/notes/cuda.html#memory-management).

Qwen's thinking mode is disabled explicitly in `apply_chat_template(enable_thinking=False)` by default, with the actual flag saved in runtime metadata. If enabled for a separately declared condition, the token budget includes thinking. Only content after a completed `</think>` delimiter is parsed as the answer. Unterminated thinking is an invalid response, never an automatic successful answer. Free-form internal thinking is not included in saved visible outputs. Both models use greedy decoding and the same configured turn/output limits; this is a controlled evaluation choice, not a reproduction of Qwen's recommended stochastic demonstration settings.

Full precision, fp16 and bf16 are selectable; optional runtime NF4 or int8 quantization uses the same selected checkpoint with a recorded bitsandbytes configuration. Do not compare configurations without disclosing their precision/runtime differences. Native Windows bitsandbytes and Qwen's optional fast DeltaNet kernels require separate compatibility testing. The project does not require FlashAttention and can use native PyTorch/SDPA paths. An unsupported fast kernel or insufficient VRAM must be logged as an actual blocker/failure, not silently worked around using cloud inference.

The application presents identical JSON tool-action instructions and read-only business observations to both models rather than using architecture-specific native tool templates. This controller protocol is an experimental constraint that may influence performance. Tool dispatch validates the allowlist, scenario permissions, visible record identifiers, exact argument names, primitive types, ranges and inventory variants before execution. It exposes no purchase, payment, update, shell or network action. Gold facts and expected outcomes are withheld from prompts.

Controller protocol version 2 exposes a cumulative `observed_facts` map alongside each observation. This map contains only canonical paths and values already returned by permitted tool calls, which makes exact claim citation accessible to both models. It contains no expected answer, required-fact list or expected tool selection. The version is recorded in configuration hashes, records and traces. The verifier preserves the original version 1 format for earlier traces with no version field. Strict JSON parsing remains unchanged: malformed output is recorded as a model protocol failure and is never repaired into a successful response. Retries use distinct run-specific trace filenames so prior failures remain reviewable.

Automatic factual checks compare explicit `{path,value}` claims against facts actually returned by authorised observations. They also assess required-fact coverage and compare validated tool names with the predefined expected set. These checks cannot identify every unsupported claim in prose. Consequently `task_success` is null and `human_review_required` is true until human review is supplied. `structured_task_success`, structured factual correctness and unsupported structured-claim rate are explicitly narrower proxies, never substitutes for assessed overall task success. Empty claim sets do not receive a perfect factual score. Tool schema validity counts both accepted and rejected proposed tool actions; no-tool cases have no schema-validity denominator.

## Runtime and evidence boundaries

All model-loading paths require previously acquired local files. They do not call a hosted inference API or automatically acquire weights. Local CUDA is mandatory for model runs, and CPU fallback is rejected. Missing inputs, dependencies, weights, native classes or CUDA produce explicit blocked records without invented performance metrics. Actual executed failures remain failures and successful smoke records remain separate from final evaluation records. The unit tests use small labelled synthetic fixtures and scripted test responses only, stored in temporary test directories.

Suggested acquisition files for Marqo are its `open_clip_config.json`, official OpenCLIP safetensors checkpoint and pinned `timm/ViT-B-16-SigLIP` tokenizer assets. For the Transformers models acquire the exact selected checkpoint's safetensors, index/configuration and tokenizer/processor assets. Check download sizes and approval requirements before acquisition. Record resolved immutable revisions; `main` is a discovery/default reference, not a reproducibility claim.
